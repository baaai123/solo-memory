## 3. 分析

### 3.1 What improved (定性飞跃)

1. **向量信号从死到活**: V2 的 all-MiniLM-L6-v2 (384-dim, 256-token) 在 self-retrieval 场景下完全失效 (0/10)。V3 的 bge-large-en-v1.5 (1024-dim, 512-token) 在 200 消息规模上达到 90% 向量召回，在 3355 规模上推动全融合召回从 60% 到 70%。

2. **为什么提升这么大**:
   - 512-token max length (vs V2 256-token) → 覆盖完整对话消息，不再截断
   - 1024-dim embedding (vs V2 384-dim) → 更大的语义区分度
   - bge-large 的预训练质量 → 更准确的语义空间

3. **全融合场景**: V3 的 RRF 融合在 200 规模达到 100%，在 3355 规模达到 70%（vs V2 的 60%）。大模型带来更强的语义信号，使 RRF 权重更容易发挥作用。

### 3.2 What degraded (代价)

1. **Ingest speed**: 25.57 → 6.75 msg/s (−3.79x)。1024-dim ONNX 推理比 384-dim sentence-transformers 慢得多。
2. **ONNX positional encoding bug**: ~375/3355 (11%) 消息因超过 512-token 限制而嵌入失败。错误信息: `BroadcastIterator::Append axis == 1 || axis == largest was false`。这些消息被跳过 (`continue`)，导致 learned_store 只有 2980 条目 vs 总 3355 消息。
3. **MiniCPM-5 rewriting not tested**: 模型加载耗时过长，消融 B (bge-large + MiniCPM-5) 未完成。

### 3.3 瓶颈诊断

| 问题 | 影响 | 优先级 |
|------|------|--------|
| ONNX pos-encoding bug | 11% 消息嵌入失败 | 🔴 高 |
| 6.75 msg/s 太慢 | 3355 条消息耗时 497s | 🟡 中 |
| 512-token max 不够 | 长消息仍被截断 | 🟡 中 |

## 4. 结论

| Question | Answer |
|----------|--------|
| bge-large 比 all-MiniLM-L6-v2 好吗？ | **是** — 召回 60%→70%，向量从 0% 到 90% |
| 向量信号是否可依赖？ | **是** — V3 向量在 200 规模达到 90% HIT |
| 物理解释是什么？ | 512-token 完整覆盖 + 1024-dim 高区分度 |
| 值得这个速度代价吗？ | **是** — 但需要修复 ONNX bug 和优化推理 |
| MiniCPM-5 rewriting 该不该加？ | 待验证（模型加载超时，手动测试延迟 ~9.8s） |

### 建议下一步

1. **修复 ONNX positional encoding bug**: 当前 bge-large 对 >512 token 的消息产生 `BroadcastIterator` 错误。需要：
   - 在 tokenizer 中显式 truncation `max_length=512`
   - 或切换到支持更长上下文的 ONNX 导出（如果存在）
2. **优化推理速度**: 考虑 GPU ONNX Runtime / TensorRT / batch embedding
3. **Bench MiniCPM-5**: 用单独脚本测试 query rewriting 对 recall 的影响
4. **扩大基准**: 测试更多查询（>10）以降低统计噪声
