# 中文记忆检索，为什么纯向量搜索救不了：一个 RRF 融合的 Agent 长期记忆实践

给 Agent 加长期记忆，现在几乎成了标配。上下文窗口再大，跨会话的偏好、决策、踩过的坑还是要存下来，下次对话再捞回来。做法也高度趋同：对话文本切成块，embedding 模型转成向量，塞进向量库，查询时算相似度召回。这套"向量检索第一"的思路在英文世界跑得很好，但一旦换成中文，问题就来了。

本文要讲的是一个开源项目 Memory Skill 的选择。它没有追向量检索的潮流，而是把 BM25 全文检索放在主信号位置，用 RRF 融合三路信号，在 300 条记忆的中文检索上做到 93% 精度、35 到 100ms 延迟。我会顺着它拆四个问题：中文检索到底难在哪，为什么 BM25 值得当主力，为什么记忆要逐字存储，以及一个记忆系统怎么自己学习。全程本地优先，零 API 检索，LLM 只用来分类和合成。

## 一、中文检索为什么难：两个世界的分词逻辑

先看一个基础事实。英文文本天然有空格，tokenize 就是把句子按空白切碎，"I use Python for backend" 切开就是五个词。主流 embedding 模型（包括 BERT 系的 tokenizer）基本都围绕这种语言结构训练，词边界明确，子词切分贴合语义单元。

中文没有空格。一句话十几个字连在一起，"我用 Python 写后端"，机器不知道哪里是词的边界。更麻烦的是，SQLite 的 FTS5 全文索引默认按空格和标点分词，对中文等于没分，整句会被当成一个 token 或者被切成单字，检索时几乎什么都匹配不上。这就是为什么项目文档里明确写着"jieba 必需，FTS5 不切中文"。

分词只是第一层问题，embedding 模型是第二层。这个项目用的向量模型是 bge-large-en-v1.5，1024 维，名字里的 en 已经说清楚了，这是英文专用模型。它的 tokenizer 在遇到中文时，会把汉字切成一堆奇怪的子词碎片，语义信息在这个过程里大量流失。中文的"记忆""上下文""检索"这些词，在英文模型的向量空间里很难表达出应有的语义关系。不是模型不好，是它没学过中文。

于是纯向量检索在中文上就变得不可靠：一方面同义改写召回强这个优势被语言错配抹掉大半，另一方面，用户记忆里大量的专有名词、库名、版本号、路径这种精确信息，向量相似度根本抓不住。而 Agent 记忆恰恰最需要抓住这些精确事实。项目在权衡里写得很直白：BGE-large-en 是英文模型，中文语义向量弱。这是承认问题，不是掩盖。

顺带说一句，如果用 jieba 做一次中文分词，效果立竿见影：

```
import jieba
print(jieba.lcut("我用Python写后端"))
# ['我', '用', 'Python', '写', '后端']
```

切出来的词就是可索引的最小语义单元，这才是中文全文检索能跑起来的起点。

## 二、BM25 主信号：RRF 融合的三个权重是怎么定的

有了一条可靠的中文分词链路，检索方案就能落地了。项目没有只留 BM25，也没有只留向量，而是三路信号做 RRF 融合：

| 信号 | 权重 | 来源 |
|---|---|---|
| BM25 全文 | 2.5 | SQLite FTS5，jieba 中文分词 |
| 语义向量 | 0.5 | ChromaDB，bge-large-en-v1.5（1024 维） |
| 时间衰减 | 0.5 | weight × exp(-0.01 × hours) |

先解释 RRF 是什么。RRF 不直接比较不同检索系统的原始分数（那些分数尺度不一样，没法相加），而是比较排序位置：对每条记忆，取它在各信号中的排名，得分是 1 除以（排名加常数 k），k 取 60。排第一得 1/61，排第十得 1/70，排名靠前的记忆被融合算法天然放大，最后乘以各信号权重求和。伪代码长这样：

```
score(d) = 2.5 * Σ 1/(k + rank_bm25(d))
         + 0.5 * Σ 1/(k + rank_vec(d))
         + 0.5 * Σ 1/(k + rank_time(d))
```

为什么 BM25 权重给到 2.5，语义和时间的 0.5 加起来才等于它的零头？项目理念里有一句话可以当答案：中文对话里 exact word match 比 vector similarity 更可靠。用户说"我用 Python 写后端"，回头查"Python 后端"时，jieba 把两边都切成同样的词，BM25 直接命中；而靠英文语义向量，这两个中文短句在向量空间里的距离未必近。精确匹配在中文记忆场景里就是比"意思差不多"更可信，权重自然给得高。

语义向量 0.5，是留一个补位：英文内容、同义改写、没命中关键词的表述，靠这路信号兜底。中英双语能并存于同一个库，靠的就是两路信号各有分工。时间衰减 0.5 再补上第三维，公式是 weight × exp(-0.01 × hours)，记忆越久越旧分越低，三天前说过的话比三个月前的"重要信息"更值得注入上下文。三条信号各管一摊：精确匹配管中文，语义管英文和改写，时间管新鲜度。

这个设计还有一个容易被忽略的好处：全部检索都在本地完成，SQLite 和 ChromaDB 都是本地库，零 API 调用，不产生检索费用。LLM 只用在分类、合成这些"需要理解"的环节。一个每天被 Agent 反复调用的记忆系统，如果每次检索都走 API，成本是扛不住的。

## 三、两半记忆模型：为什么必须逐字存储

检索方案定了，接下来是存什么的问题。项目把记忆分成两半。

非结构化侧叫 user_mem，存对话原文，逐字存储，进 DialogueStore（SQLite FTS5，供 BM25）和 LearnedStore（ChromaDB，供向量），每条记忆用 title、time、vector、id 四元组索引。结构化侧是 pref、pers、skill、mission 四类，由 LLM 做 classify_and_extract 后路由：偏好存键值对，人格累积成人物卡，技能存学习目标文档，任务存步骤清单。

设计原则只有八个字：Never summarize，Store verbatim。绝不摘要，只存原文。

这条原则很多人会忽略，但它是整个系统的地基。摘要会丢语境、丢态度、丢细节。"我觉得 Docker 有点难"和"我用 Docker 部署失败了三次"，摘要模型很可能都压缩成"用户提到 Docker"，但前者是情绪，后者是明确的踩坑记录，对后续回答的影响完全不同。记忆系统做的是取证，不是总结。你可以在读的时候自己决定什么重要，但如果在写的时候就把信息压掉，等于替未来的自己做了判断，而这个判断往往错。

所以这个项目把摘要的活儿只留给结构化侧，而且结构化的目标是长期知识文档，不是对话压缩。user_mem 永远存原文，检索时 BM25 命中原文段落，直接注入上下文。技能、任务这类需要"理解"的，才让 LLM 合成 markdown 文档。

写入链路是三级：先 ingest_dialogue 把对话进两半库，再 tag_title 用 LLM 生成标题挂到 ChromaDB metadata，最后 extract_structured 做结构化路由。读的时候，weave 组装 8 个区块：人格设定、用户偏好、当前场景、最近对话、检索记忆、已掌握技能、当前任务、知识缺口，按 tier1 场景感知、tier2 对话片段、nudge 高优记忆三层注入。Agent 还可以主动引用记忆标题，让系统展开成完整上下文。存是逐字的，取是多层的，两端各干各的活。

## 四、自我学习闭环：从"记住"到"学会"

存和取解决了"记住"，项目还有一条链路解决"学会"。管道是固定的五段：

```
GapDetector → LearningDecider → WebCrawler → KnowledgeSynth → verify
```

GapDetector 在每次 weave 时检查知识缺口，把"用户问了个我不会的东西"暴露出来。LearningDecider 做决策，输出 skip、ask、learn 三选一，要不要学由它判断而不是无条件开爬。决定学习后，WebCrawler 爬取给定 URL，KnowledgeSynth 用 LLM 把素材合成成技能文档，写入 skill 分支，最后走一轮验证闭环。

对应到工具就是 memory_gaps 查看缺口、memory_learn 触发学习。这套闭环的意义在于：记忆系统不只是存储库，它会自己成长。今天爬下来的 Docker 部署步骤，明天就成了注入上下文的"已掌握技能"。

值得注意的还是那个边界：LLM 在这个系统里只出现在分类、合成、决策这些需要理解的环节，检索、存储、权重演化全部本地完成。反馈机制也是本地算的，去重加分 0.05、引用加分 0.02、用户反馈加分 0.05，记忆权重随使用自动演化，用得多的记忆排名自然靠前。这套"理解靠 LLM，检索靠本地"的分工，是这个项目本地优先定位的直接体现。

## 五、数据与反思

项目公布的数字，全部来自它自己的仓库：中文检索精度 93%（300 条记忆规模），检索延迟 35 到 100ms，测试 46 个快速用例（0.07s，纯内存）加 65 个集成用例。坦白说，300 条规模不算大，93% 是单点数据，不是大规模 benchmark，但这些数字至少说明一个方向是对的：不用大模型检索，靠本地 BM25 加 RRF，也能在中文记忆上做到够用的精度和毫秒级延迟。

有几个权衡值得正视。一是 bge-large-en-v1.5 是英文模型，中文语义信号偏弱，项目用 BM25 主信号补足，如果哪天想要单模型统一中英语义检索，可以换 bge-m3 这种多语言模型，代价是要重新嵌入历史记忆。二是结构化提取依赖 LLM 质量，classify prompt 用示例来稳定输出。三是 jieba 是硬依赖，分词质量直接决定 BM25 上限。

拿 Mem0、Letta 这类系统做机制对比，结论也很清楚，不涉及好坏。Letta 走的是 MemGPT 式的上下文管理，靠 embedding 和摘要维持"记得像没记过"的体验；Mem0 是向量检索加图记忆的代表。它们把筹码押在语义理解上，这在英文场景合理，因为英文 embedding 足够可靠。这个项目反过来，把筹码押在精确匹配上，因为中文场景里精确匹配比向量相似度更可信，而且本地零成本。两者是不同权衡下的合理选择，谈不上谁碾压谁。只是如果你做的是中文 Agent，得先想清楚：你的 embedding 模型，真的懂中文吗？

## 结语

回到开头的问题。中文记忆检索难，难在分词、难在英文 embedding 模型对中文不友好、难在向量相似度抓不住精确事实。Memory Skill 的答案不花哨：jieba 解决分词，BM25 当主信号解决精确匹配，语义向量和时间衰减各司其职，RRF 用排名融合绕开不同信号分数不可比的问题。加上逐字存储和主动学习闭环，一个本地优先、中英双语、能自我进化的记忆系统就立起来了。

对做中文 Agent 的人来说，最大的启示可能不是这套权重抄回去就能用，而是一个检索方法论的提醒：先确认你的语料语言和你的 embedding 模型语言匹配，再决定向量该拿多少权重。工具没有绝对的好坏，只有适不适合你的语言。
